# 소수 E2E 원천 재사용과 시간 비교

상태: 2026-11-27 같은 코드의 실제 새 수집/재사용·실패 실행을 대조했습니다. 적용은 기존 개발용 두 법인의 수동 E2E에 한정합니다. [이전 실행](small-cash-e2e-2026.md)에서는 API 7·웹 4회에 약 301초가 걸렸고 법인 코드 ZIP 수신이 약 236.59초였습니다. 네트워크 상태가 다른 날짜의 한 실행으로 속도 향상을 단정하지 않습니다.

## 원천 재사용 경계

사용자가 지정한 이전 수집 실행의 데이터 브랜치를 읽습니다. requests.json이 있으면 응답별 체크포인트를, 없으면 이전 report.json의 요청 기록을 사용합니다. 한국 시각 같은 날짜에 실제 받은 법인 코드 ZIP과 동일 접수번호 document.xml만 재사용합니다. 요청 파라미터·관측 시각·크기·SHA-256·루트 안 파일 경로를 검증합니다. 재사용 기록을 다시 재사용해도 최초 실제 관측 시각을 유지하며 나이를 새로 만들지 않습니다. 모순된 원천이나 손상·미래·다른 날짜·미완료 원천은 사용하지 않고 새 수집합니다. 선택한 재사용 원천이 없거나 잘못된 입력이면 없는 데이터를 성공으로 취급하지 않습니다.

기업개황·전체 유형 공시 목록·본문 관계·표는 매번 새로 받습니다. 이전 명칭·상장 여부·정정 관계를 현재 관측으로 위장하지 않습니다. 실제 전수 법인 명부 캐시 정책을 확정하거나 자료/판정 기준을 완화한 것이 아닙니다. 같은 날짜에 수집한 원문 재사용은 명시한 개발용 실행에서의 범위이며 원천 기관의 장중 변경이 절대 없다는 보장을 의미하지 않습니다.

## 수집 중단과 재실행

응답을 받을 때마다 기존 인증키 검사 뒤 원천 파일과 requests.json을 임시 파일에서 교체해 저장합니다. 받는 도중 종료된 응답은 완료 해시가 없어 다음 실행에서 쓰지 않습니다. 최종 report.json이 없어도 완료된 원천은 재사용할 수 있습니다. 후속 실행은 기업개황·목록·본문과 조회를 다시 실행합니다. 계산 중간 상태나 오래된 최종 금액을 그대로 이어받지 않습니다.

GitHub 소수 실행에는 Linux timeout으로 전체 360초 제한과 5초 강제 종료 유예를 둡니다. 기존 요청 소켓 제한·32MiB/웹 2MiB·API 20회/웹 6회는 유지합니다. 종료/실패 시에도 이미 안전하게 저장된 부분 원천을 별도 데이터 브랜치로 보존합니다. 잡의 실패 상태를 성공으로 바꾸지 않습니다. 워크플로 전체 취소·러너 강제 종료·브랜치 push 실패 시 원격 보관까지 보장하지는 못합니다. 다른 기존 수집 모드는 바꾸지 않습니다.

## 실행 방법과 비교 기준

기존 Collect DART filings에서 small_cash_e2e·두 종목·명시한 제출일 구간을 사용합니다. reuse_run_id가 비어 있으면 새로 수집하고 이전 실행번호를 주면 해당 공개 데이터 브랜치의 원천을 검사합니다. 새 시크릿·권한·의존성·상시 봇·자동 재시도는 없습니다.

같은 한국 날짜·같은 두 종목·같은 제출일 구간·같은 코드로 새 수집과 재사용 실행을 비교합니다. API 실제 호출·재사용 횟수·웹 요청·실제 네트워크 응답 바이트·전체 시간과 법인별 기준일/금액/원문 해시/링크를 확인합니다. 같은 요청을 처리한 논리 기록과 실제 네트워크 요청 수를 섞지 않습니다. 오늘의 새 목록/기업개황 결과가 달라지면 이전 금액에 맞춰 고치지 않습니다. 이전 개발용 원문 대조값은 기존 평가 문서에 고정돼 있습니다.

## 고정 응답 검증

같은 날짜·정확한 접수번호만 사용하는지, 다른 날짜/미래/시각 정보 없음/해시·크기 불일치/경로 이탈/미완료/충돌 원천을 거절하는지 검사합니다. 최종 보고서 없이 체크포인트에서 재실행하면 법인 코드·원문은 재사용하지만 기업개황·목록·본문은 새로 요청하는지 확인합니다. 새 기업개황에서 대상 식별이 맞지 않으면 재사용 법인 코드가 있어도 보류합니다. 실패·인증키 검사 거절 응답은 재사용 원천으로 저장하지 않습니다.

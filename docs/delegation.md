# 에이전트에게 맡기는 범위

상태: 2026-11-20 사용자와 합의했습니다. 일반 작업은 에이전트가 구현·검사·PR·병합·정리까지 처리합니다. 중요한 기준 변경과 예외만 사용자에게 확인합니다.

## 작업 구분

| 에이전트가 처리할 수 있는 작업 | 사용자 확인이 필요한 변경 |
|---|---|
| 합의한 명세를 구현 | 요구사항·조회·판정 기준 변경 |
| 기준을 유지하는 버그 수정 | 기존 테스트 정답·기대 결과 변경 |
| 설명·링크·작업 상태 갱신 | CI 검사 완화·제외·권한 변경 |
| 테스트 추가·코드 정리 | 새 외부 의존성·비용 추가 |
| 완료한 브랜치·이슈 정리 | 근거 부족·반복 실패·판단이 애매한 작업 |

파일 종류만으로 판단하지 않습니다. 문서 수정이어도 요구사항을 바꾸면 확인 대상입니다. 버그 수정이라고 불러도 기대하는 결과 자체가 달라지면 먼저 확인합니다. 신규 테스트는 승인한 기준의 사례를 추가할 수 있지만 기존 정답을 바꿔 실패를 없애면 안 됩니다.

## 에이전트가 병합하기 전 확인할 것

1. 관련 이슈와 docs의 완료 조건을 충족합니다.
2. 변경 전체가 위임 범위인지 확인합니다. 일부라도 판단이 어려우면 사용자에게 질문합니다.
3. 실제 코드·문서 차이와 테스트·검사 기준 변경을 확인하고 PR에 이유와 근거를 적습니다.
4. 최신 main과 통합한 변경에서 필수 CI가 통과해야 합니다. 검사 실패나 대기 상태를 무시하거나 관리자 우회로 병합하지 않습니다.
5. 검사한 커밋과 병합할 커밋이 같아야 합니다. 병합 API에는 예상 head SHA를 전달해 사이에 변경됐으면 중단합니다.
6. 병합 후 이슈 본문·체크리스트·상태를 최신화하고 원격 브랜치 삭제를 확인합니다.

위 조건을 충족하면 PR마다 별도 병합 승인을 요청하지 않습니다. 사용자가 특정 작업에 검토·보류를 요청하면 그 지시를 우선합니다. 실패가 반복되면 검사 규칙을 낮추지 말고 원인·시도·추천 조치를 보고합니다.

## 사용자에게 질문할 때

질문 하나에 현재 문제, 추천안, 이유, 영향, 관련 문서·PR 링크를 묶습니다. 사용자가 확인할 필요가 없는 코드 세부사항과 이미 끝난 설정 요청을 반복하지 않습니다.

## 무엇이 자동화됐나요?

현재는 작업 중인 에이전트가 범위를 판단하고 검사 결과를 확인한 뒤 GitHub API·CLI로 병합합니다. GitHub Actions의 자동 병합 봇이나 상시 실행 에이전트를 활성화한 것은 아닙니다.

build·code-quality와 main 보호는 기계적 제약입니다. 변경의 의미가 승인 범위인지, 기존 정답을 약하게 바꿨는지는 CI가 모두 판단하지 못합니다. 작성과 자기 리뷰를 독립적인 사람 승인이라고 표현하지 않습니다. PR·검사·원문 근거를 보존하고 사용자가 일부 완료 작업을 확인할 수 있게 합니다.

이 위임 정책 자체를 확대하거나 사용자 확인 대상을 줄이는 변경은 사용자 확인을 받습니다. 예외를 과거 승인에서 임의로 확대 해석하지 않습니다.

## 첫 적용

PR #10은 이미 요청받은 DART 수집 구현이고, 새 권한·외부 의존성·판정 기준 변경이나 CI 완화가 없었습니다. 최신 main 통합 후 두 필수 CI와 실제 수집 성공 기록을 확인하고 이 정책에 따라 병합했습니다. 이후 기록은 관련 이슈와 PR에서 추적합니다.

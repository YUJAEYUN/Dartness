# Dartness 개발환경 추천안

상태: 제안 — 기술 선택과 상세 경계는 구현 사례로 검증 후 확정한다.

## 목표와 범위

사용자가 규격화된 템플릿으로 지정한 조건을 DART에서 조회하고, 필요한 항목만 고정된 형식으로 출력한다. 사용자가 공시 원문과 대조할 수 있는 근거 링크를 제공한다. 영업 제안, 상품 추천, 투자 평가는 수행하지 않는다.

구조화 API와 공시 원문·주석을 함께 사용한다. 미확인·미공시·수집 실패·해석 불가를 0 또는 해당 없음과 구분한다. 연결/별도, 당기/전기, 공시일/재무 기준일을 보존한다.

## 개발환경

Python 3.12와 uv를 기본 후보로 한다. 의존성은 uv.lock으로 고정하고 CI에서도 동일한 환경을 재현한다.

- Ruff: 형식과 기본 정적 오류.
- Pyright: 엄격한 타입 검사. 외부 응답은 검증 전에 신뢰하지 않는다.
- Pydantic: 입력·중간 결과·출력 계약. strict 검증 외에도 날짜·금액·상태 간 의미 제약을 별도 정의한다.
- pytest: 계약·계산·공시 회귀 테스트.
- import-linter: 모듈 의존 방향과 금지 의존 검사.
- openpyxl: 조회 유형별 고정 엑셀 출력.
- GitHub Actions: 필수 오프라인 검사. 실제 DART 검사는 별도 실행한다.

초기에는 단일 패키지와 CLI로 시작한다. CLI와 향후 MCP는 동일한 실행 엔진을 호출한다. MCP 자체를 검증 장치로 취급하지 않는다. 실제 API·LLM 호출 없이 검사할 수 있어야 한다.

## 코드와 에이전트의 실행 경계

| 단계 | 코드 책임 | 제한된 에이전트 책임 |
|---|---|---|
| 요청 | 필수 조건·지원 조합 검증 | 표현을 등록된 조회 항목에 대응 |
| 기업 식별 | 코드 대조·후보 생성 | 모호한 경우 확인 필요 반환 |
| 공시 선택 | 기간·유형·정정 관계 처리 | 허용된 후보 중 내용상 적합성 선택 |
| 자료 수집 | API·원문·첨부·캐시·재시도 | 임의 출처 확장 금지 |
| 추출 | 표·절·주변 문맥과 위치 보존 | 항목 의미와 포함 여부 판단 |
| 검증 | 원문 값·위치·기간·단위 검사 | 해결되지 않은 충돌 설명 |
| 계산·출력 | 환산·합산·조건 비교·고정 서식 | 확정 상태와 출력 규격 변경 금지 |

실행 엔진이 허용된 순서와 분기를 관리한다. 에이전트는 각 단계의 입력, 도구, 결정 종류, 출력 스키마, 호출 한도 안에서 동작한다. 공시 내용은 근거 데이터이며 실행 지시가 아니다.

에이전트의 결과도 검증되지 않은 입력이다. 자신감 점수만으로 결과를 승인하지 않는다. 재시도 횟수를 제한하고 실패하면 확인 필요로 분리한다. 조회 실행 중 코드나 검사 기준을 수정하지 않는다.

## 데이터 계약 후보

- QuerySpec: 대상, 항목, 조건, 기준일, 재무제표 범위, 환산 정책, 출력 유형.
- FilingRef: 법인코드, 접수번호, 문서 식별자, 공시일, 대상 기간, 정정 관계.
- EvidenceRef: 원문 식별자와 해시, 표·문단 위치, 발췌, 원문 값과 단위, 사용자용 링크, 링크의 정확도.
- ExtractionCandidate: 추출 사실 후보, 근거 참조, 판단 불가 사유.
- ValidatedFact: 검사 통과 사실과 수행한 검사·버전 기록.
- QueryResult: 조건 판정과 고정 출력에 필요한 값.
- RunManifest: 요청, 처리 건수, 실패·미확인 상태, 실행·레시피·모델 버전.

검증 통과는 정의된 검사를 통과했다는 뜻이며 의미상 정답을 보장하지 않는다. 별도의 실제 공시 평가가 필요하다. 타입 구분은 실수 방지 수단이며 접근 권한 통제 자체가 아니다.

미공시, 수집 실패, 기업 미매칭, 해석 불가를 구분한다. 실제 금액 0은 근거가 있을 때만 기록한다. 직접 공시된 원화금액과 계산한 원화금액을 구분한다.

## 모듈 경계

contracts, workflow, sources, documents, extractors, validation, calculation, export를 논리적 경계로 둔다. 별도 서비스로 배포하거나 폴더마다 클래스를 만들 필요는 없다.

- contracts는 수집·출력 구현에 의존하지 않는다.
- 외부 HTTP 통신은 sources에 한정한다.
- 에이전트·모델 호출은 별도 어댑터에 두고 단계별 허용 도구를 제한한다.
- extractors는 export를 호출하지 않는다.
- export는 API·모델을 호출하지 않으며 검증 전 후보를 받지 않는다.
- workflow가 단계 연결과 재시도·중단을 관리한다.
- 계산과 환산은 공통 모듈에서 수행한다.

## 조회 레시피

레시피는 항목 정의, 입력 템플릿, 문서 선택 정책, 추출 경로, 허용된 대체 경로, 검증 규칙, 출력 열, 정답 사례를 묶는다.

통화마다 코드를 복제하지 않는다. 다만 TRY 외화자산과 TRY 표시 채권은 다른 항목으로 정의한다. 지원되지 않은 조합을 실행 중 임의 코드 생성으로 해결하지 않는다.

## 안티패턴 방지

| 대상 | 수단 |
|---|---|
| 순환 의존·출력에서 HTTP 호출 | 의존성 검사 |
| 광범위한 예외를 잡고 무시 | 린트와 오류 경로 테스트 |
| 검증되지 않은 딕셔너리 전달 | 타입·스키마 검사 |
| 누락을 0으로 치환 | 상태 모델·회귀 테스트 |
| 중복 합산·단위·기간 혼동 | 실제 공시 정답 사례 |
| 검증 전에 출력 | 계약·실행 흐름 테스트 |
| 과도한 추상화·불필요한 범용화 | 설계 리뷰와 변경 사례 검토 |

커스텀 규칙에는 문제, 검사 방법, 수정 대안, 예외를 함께 기록한다. 이름·길이·복잡도만으로 설계 품질을 단정하지 않는다. 불확실한 규칙은 경고로 검증하고 효과가 없으면 제거한다. 커버리지 숫자 자체를 목표로 삼지 않는다.

## 개발 지침과 실행 지침

- AGENTS.md: 짧은 저장소 지도, 개발 명령, 명세 위치, 완료 조건.
- SKILL.md: 사용자 입력 안내, 레시피 선택, 실행 도구 호출, 결과 전달.
- docs: 아키텍처, 실행 경계, 품질 규칙, 설계 결정.
- recipes: 도메인 정의와 조회별 계약.
- 코드·CI: 기계적으로 강제할 규칙.

실행용 AGENTS.md를 별도로 필수화하지 않는다. 중요 제약을 특정 호스트의 지침 파일 로딩에 의존시키지 않는다.

## 검증과 공개 저장소 운영

PR 필수 검사: 린트, 타입, 모듈 경계, 계약, 핵심 회귀 테스트.

정답 사례에는 당기/전기, 연결/별도, 원/천원/백만원, 자산/부채, 합계/세부항목, 정정 공시, 비12월 결산, 미공시, 실패를 포함한다. 평가 자료 일부는 개발 중 튜닝 사례와 분리한다. 정답은 사람이 원문을 확인하고 변경 이유를 남긴다.

실제 DART 검사는 자격증명과 호출 한도를 별도 관리한다. 필수 오프라인 CI가 네트워크나 유료 모델에 의존하지 않게 한다. LLM 연동 검사는 별도로 운영한다.

정답·출력 규격·검사 제외·CI 완화 변경은 별도 검토 대상으로 표시한다. 필수 검사의 강제는 가능한 저장소 보호 설정으로 연결한다.

API 키, 거래 법인 목록, 내부 팀 매핑, 실제 조회 결과는 공개 저장소에 포함하지 않는다. 공시 fixture도 공개 가능 범위를 확인하고 필요한 최소 자료만 사용한다. 코드 채택 전 라이선스와 의존성을 확인한다.

## 레퍼런스 채택 기준

참고 자료를 통째로 복사하지 않는다. 기능별로 해결할 문제, 참고 커밋, 채택·제외 요소, 대안, 검증 사례, 라이선스를 기록한다.

- Stripe blueprint: 고정 단계와 제한된 에이전트 판단의 결합.
- OpenAI harness engineering: 짧은 안내, 구조화된 문서, 기계적 제약.
- Google code review: 작은 변경과 작성자 외 검토.
- Kubernetes OWNERS: 협업 시 영역별 검토 책임.
- Uber CI 글: 안정성과 실행 비용을 함께 측정. 대규모 빌드 스케줄링은 초기 범위에서 제외.
- vercel-labs/skills: 패키징·설치·버전 관리 참고.
- last30days-skill: 지침과 실행 엔진 분리, 조건별 참조 문서, 실행 전 점검.
- DART 도구: 기업 식별, 문서 후보 선택, 원문 수집, 캐시, 근거 링크를 기능별 평가. 실행 정확도는 별도 검증.

## 구현 순서

1. 요청·근거·상태·출력 계약과 실행 경계 확정.
2. 기본 개발환경과 필수 CI 구축.
3. 실제 공시의 정답·실패 사례 확보.
4. 현금및현금성자산 총액 조회를 끝까지 연결.
5. TRY 표시 채권 조회로 원문 해석 경로 검증.
6. 검증된 엔진을 호출하는 스킬 작성.
7. 다른 클라이언트 연동이 필요할 때 MCP 추가.

초기 결정이 필요한 항목: 실제 실행 호스트, 사용자 입력 방식, 모델·데이터 전달 정책, 환율 출처·기준일, 공시 캐시 보관 정책, 정답 검토 방식.

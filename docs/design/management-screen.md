# 작업 관리 화면

상태: 사용자가 React + shadcn/ui 조회용 화면과 GitHub 상태 스냅샷 방식을 승인했습니다. 구현은 dashboard/에 있습니다. 로그인·쓰기 서버·상시 실행은 없습니다. GitHub 공개 상태는 화면 열기·다시 확인 시 조회합니다. [위임 범위](../guides/delegation.md)는 그대로 적용합니다.

사용자는 중요한 결정과 예외를 먼저 봅니다. 일반 작업은 에이전트가 처리하고, 완료 요약·검사·결과물·원문 링크를 남깁니다.

### 첫 화면의 시스템 상태

[시스템 상태](../system-status.md)의 Mermaid 흐름도, 단계별 상태·남은 범위·코드와 테스트 근거, 아직 정하지 않은 질문, 지금·다음·나중 작업을 첫 화면에서 읽습니다. 단계 버튼을 누르면 해당 범위와 근거를 펼칩니다. 흐름도 렌더링에 실패해도 같은 데이터를 읽는 단계 목록과 설명은 남습니다.

미결 항목은 아직 정하지 않은 목록이며 모두 즉시 답할 승인 요청은 아닙니다. 다음 작업의 제안·보류 상태는 원문 그대로 표시합니다. 과거 현금 범위 결정과 '추출기 미구현' 문구를 별도 카드에 수동 보관하지 않습니다. 확정한 기준은 [요구사항](../specs/requirements.md#cash-scope)에서 확인합니다.

### 현재 기준

카드에는 대상 이슈·PR, 마지막 갱신 시각, 근거 링크를 둡니다. 에이전트의 요약과 실제 CI 결과를 구분합니다. GitHub가 닫힘이면 화면에서 진행 중으로 계속 남지 않도록 갱신하며, 조회 실패를 이슈 종료로 해석하지 않습니다.

## 구현 범위

React + TypeScript + Vite와 shadcn/ui Button을 바탕으로 만든 정적 화면입니다. 기존 공개 GitHub 조회 모듈을 브라우저에서도 재사용하고 한국 시간으로 확인 시각을 표시합니다. 조회 실패 시 배포 저장본 또는 직전 정상 자료를 표시하며 지속적인 실시간 감시라고 표현하지 않습니다. 토큰을 번들·HTML·상태 JSON에 넣지 않습니다. API에서 받은 제목·본문은 신뢰하지 않는 텍스트로 렌더링합니다.

승인·병합 버튼과 로그인·쓰기 서버·정기 실행은 후속 범위입니다. 문서 사이트는 계속 docs를 렌더링하고 관리 화면은 링크로 연결합니다. 범용 UI 라이브러리는 외부 DART MCP·래퍼를 쓰지 않는 결정과 별개지만, 이번 React·shadcn/ui 구현 도입은 사용자에게 확인했습니다.

## 완료를 어떻게 확인하나요?

- 사용자가 첫 화면에서 자신이 답할 질문과 이유를 찾을 수 있습니다.
- 완료 작업에서 PR·검사·결과물로 이동할 수 있습니다.
- 갱신 시각과 원본이 있어 오래된 상태를 구분할 수 있습니다.
- 사용자 확인 대상이 아닌 일반 작업에 매번 승인 카드를 만들지 않습니다.
- 키·내부 법인 목록·불필요한 원문 데이터는 화면에 싣지 않습니다.

## 실행과 갱신

Node.js 24가 필요합니다. 저장소 루트에서 `cd dashboard`, `npm ci`, `npm run dev`로 엽니다. 정적 결과물은 `npm run build`가 만드는 dashboard/dist/입니다. 사용자는 Vercel 배포를 선택했습니다. Root Directory는 dashboard, 빌드는 npm run build, 출력은 dist, 운영 브랜치는 main입니다. 운영 주소는 [Dartness](https://dartness.vercel.app/)이며 PR·이슈의 배포 근거와 대조합니다.

`npm run snapshot`은 공식 GitHub 공개 API에서 인증 없이 이슈·PR·main 검사 상태를 읽어 public/data/snapshot.json에 저장합니다. Vercel 빌드(VERCEL=1)에서는 npm run build가 이 갱신을 먼저 실행합니다. 제목·번호·상태·원본 URL·시각만 허용하며 토큰·본문·사용자 정보는 포함하지 않습니다. 조회 실패는 비정상 종료하고 이전 파일을 유지합니다. 2026-11-24 사용자 승인으로 Vercel 빌드는 최신 조회 실패 시 기존 저장본을 화면과 같은 형식·원본 링크 검사로 검증하고, 유효하면 경고를 남긴 뒤 배포합니다. 저장본의 내용·확인 시각은 바꾸지 않습니다. 저장본이 없거나 잘못됐으면 빌드가 실패합니다. 디스크 쓰기 오류도 실패하며 숨기지 않습니다. 수동 npm run snapshot은 계속 조회 실패 시 비정상 종료합니다. 각 요청은 15초 제한이며 재시도하지 않습니다. 공개 API 호출 제한(429 등)도 실패로 처리합니다. 최대 최근 100건이며 한도에 닿으면 화면에 표시합니다. 검사 이력은 최근 10건이며 전체 이력은 GitHub 링크에서 확인합니다.

화면 열기와 다시 확인은 공개 GitHub API를 조회합니다. 이슈만 닫아도 다음 화면 조회에서 반영되며 새 배포를 요구하지 않습니다. 조회 성공 전까지 마지막 정상 자료를 유지하고, 최초 조회 실패 시 배포 저장본을 사용합니다. Vercel의 빌드 시 저장본 생성도 유지합니다. 일반 CI와 로컬 빌드는 외부 요청 없이 저장된 JSON을 사용합니다. 24시간이 지난 자료와 미래 시각은 주의 표시를 합니다. 이 기준은 작업 현황의 표시용이며 DART 공시 판단 기준과 무관합니다.

시스템 상태와 미결 항목은 docs에서 생성하며 화면의 별도 문구로 관리하지 않습니다. GitHub 조회/대체 자료와 배포 커밋에 고정된 docs의 구현 상태는 다른 시점·출처임을 구분합니다. 이슈 전체를 LLM으로 분류하거나 모든 예외를 자동 발견하지 않습니다.

## 검사와 현재 한계

기존 필수 code-quality에 UI 린트·Vitest·TypeScript strict·빌드를 추가했습니다. 기존 Python 검사와 docs 빌드는 유지합니다. Vitest는 누락된 자료, 출처·링크 검증, 오래된 시각과 후속 성공이 있는 과거 실패를 검사합니다. CI는 정적 결과물을 management-dashboard 아티팩트로 저장합니다. GitHub 원본의 향후 변경이나 문서·코드의 의미 일치를 증명하지는 않습니다.

초기 구현의 브라우저 확인은 보류했으나 이슈 #29에서 설치된 headless Chromium으로 기본 화면을 확인했습니다. 상세 모바일 검토는 계속 보류합니다. 실제 운영 URL과 배포 커밋·문서/브리핑 해시는 각 작업의 이슈·PR에서 확인합니다. 반응형 CSS와 빌드 성공을 시각 검증 완료라고 표현하지 않습니다.

2026-11-20 사용자가 운영 화면 접속을 확인했습니다. 초기 단계에서는 상세 모바일·클릭 검토를 보류하고 데이터 계약·공시 검증을 우선하기로 합의했습니다. 이슈 #13은 종료했으며 UI 빌드·타입·핵심 데이터 CI는 유지합니다. 이는 에이전트의 브라우저 시각 검증 완료를 뜻하지 않습니다.

## docs·코드·화면 동기화

원본은 docs/system-status.md입니다. dashboard/scripts/system-status.mjs가 흐름도와 stages·next·decisions·rules 표를 읽어 dashboard/src/generated/system-status.json을 생성합니다. 생성 파일은 직접 수정하지 않습니다. 원본 해시는 화면에서 확인할 수 있고 같은 배포 코드에 포함됩니다. docs의 다음 작업·결정·구현 상태를 바꾸면 dashboard에서 `npm run docs:generate`로 재생성해 함께 커밋합니다. 빌드도 먼저 재생성하며 원본이 없거나 모호하면 실패합니다.

기존 필수 code-quality는 빌드 전에 `npm run docs:check`로 커밋된 생성물과 원본의 정확한 일치를 검사합니다. 원본 표 표시 누락·중복, 잘못된 상태, 흐름도 이름/색과 표의 불일치, 없는 근거 파일, 구현 단계의 코드·테스트 근거 누락, 없는 단계로 연결한 미결 질문도 실패합니다. 기존 문서 예시·경로·규칙·상태 지도 검사와 Python·UI 검사는 유지합니다.

로컬은 dashboard에서 `npm run hooks:install`을 한 번 실행하면 pre-commit 훅이 변경 형식과 생성물 일치를 확인합니다. 새 체크아웃에서는 각자 설치해야 하며 훅은 우회할 수 있으므로 최종 강제력은 필수 CI입니다. 현재 작업 환경에는 설치했습니다. 훅은 파일을 자동 수정하거나 stage하지 않습니다.

이 검사는 docs에 적은 연결과 생성 결과를 확인합니다. 구현 상태 판단의 진실성, 원문 추출의 정확도, 모든 코드 변경이 문서 수정을 요구하는지는 자동 증명하지 않습니다. 계약 테스트·실제 사례 평가·변경 검토로 보완합니다. '구현'은 코드·테스트 근거가 있다는 범위이며 모든 공시를 처리한다는 뜻이 아닙니다.

Mermaid는 요청한 흐름도를 브라우저에서 strict 보안 모드로 렌더링합니다. 원문 HTML을 렌더링하지 않고 외부 링크 실행 지시가 든 흐름도는 생성 시 거절합니다. 브라우저·모바일 상세 검토 보류는 유지합니다.

이슈 #29의 기본 브라우저 확인: Mermaid SVG 한 개, 단계 버튼 9개, 미결 항목 6개를 확인했고 현금 추출 단계 버튼이 남은 범위·근거 설명을 바꾸는지 검사했습니다. 해당 로컬 실행의 페이지 오류는 없었습니다. 이는 모든 브라우저·모바일·상호작용을 검증한 결과는 아닙니다.

Vercel이 제공한 배포 커밋 SHA로 docs·코드·테스트 근거 링크를 고정합니다. 이후 main이 바뀌어도 해당 화면이 설명하는 버전으로 이동합니다. 로컬이나 SHA가 없는 빌드는 main을 참조합니다. GitHub 이슈·PR 상태 링크는 계속 실제 작업 원본을 가리킵니다.

## 올인원 조회 범위

docs/specs/query-types.md의 query-types 표를 같은 생성기가 읽어 다섯 유형의 입력·결과·근거·미결·구현 상태를 첫 화면 카드로 표시합니다. 별도 원본 해시와 문서 링크를 제공하며 상태와 중복 ID·빈 표·누락된 열을 검사합니다. 원본 파일 변경은 기존 docs:check로 생성물 불일치가 드러납니다. 현금 외 유형에 실행 버튼이나 지원 완료 표시를 붙이지 않습니다. 아래 흐름도는 현금의 첫 경로이며 전체 유형 구현 지도가 아닙니다.

GitHub의 open은 보류된 작업도 포함하므로 화면에서 열린 작업으로 표시합니다. 실제 진행·보류·제안은 docs의 개발 순서와 해당 이슈에서 확인합니다. open만으로 진행 중이라고 단정하지 않습니다.

## 작업 브리핑

"작업 브리핑" 칸은 docs/briefings/의 브리핑을 최신 PR부터 목록으로 보여주고, 고른 작업의 요약·확인할 질문·바뀐 단계·결정 주체·확인 범위·근거를 표시합니다. 원본과 생성 방식, 표시할 수 있는 형식은 [작업 브리핑](../briefings/index.md)을 따릅니다. 브리핑은 PR을 요약한 2차 자료이며, 화면은 PR·코드·테스트로 가는 링크를 함께 둡니다. 브리핑을 쓰지 않은 PR은 이 칸에 나오지 않습니다.

## 합의한 공통 조회 조건

docs/specs/common-query-contract.md의 query-policy 표를 같은 생성기로 읽어 정책 목록과 원본 해시를 화면에 표시합니다. 단일 조회·세 시장 전수·기준일·이전 자료·경과 한도·공시 마감·정정·출력 옵션·내부 기록을 확인할 수 있습니다. 정책 합의와 엔진 구현은 구분하며 단계의 구현 상태는 자동으로 올리지 않습니다. 생성물 일치 검사는 이 원본 변경도 확인합니다.

## 최신 GitHub 상태 조회 — 변경 기준

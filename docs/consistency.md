# 문서·위키·코드 정합성 검토

상태: 검토 절차의 첫 버전. 의미 비교를 자동 수행하는 프로그램은 아직 없습니다.

프로젝트 기준은 사람이 읽는 docs입니다. 위키는 이를 찾아주는 지도이며, 코드는 기준을 구현합니다. 차이가 생기면 문서를 코드에 자동으로 맞추지 않습니다.

## 세 관계를 확인합니다

| 관계 | 검토 내용 |
|---|---|
| 기준 문서 ↔ 코드 | 조건·예외가 구현됐는가? 명세 밖의 추정·대체 동작이 있는가? |
| 기준 문서 ↔ 위키 | 중요한 조건을 누락하거나 뜻을 바꾸지 않았는가? |
| 위키 ↔ 코드 | 안내한 구현·테스트가 존재하며 설명과 맞는가? |

## 중요한 규칙의 연결

오판·누락·출력 변화에 영향을 주는 규칙에만 안정적인 식별자를 붙입니다. 모든 문장에 번호를 만들지 않습니다. 규칙 원문은 해당 도메인 문서에 두고, 아래 기록에는 참조와 검토 근거를 남깁니다. 폐기한 식별자는 다른 의미로 재사용하지 않습니다.

[검토 기록 양식](record-forms/consistency-review.md)에서 범위, 기준 커밋, 문서 위치, 구현·테스트·위키 위치, 관찰한 차이와 한계를 기록합니다. 존재하지 않는 구현 경로는 만들지 않고 미구현으로 씁니다.

## 검토 상태

| 상태 | 의미 |
|---|---|
| 검토상 일치 | 명시한 버전·범위에서 구현·테스트·위키를 확인했고 차이를 찾지 못함 |
| 불일치 | 구체적인 충돌·누락 발견 |
| 미구현 | 기준은 있으나 구현이 없음 |
| 판단 보류 | 기준이 모호하거나 검증 근거 부족 |
| 재검토 필요 | 관련 기준·구현·테스트·위키가 마지막 검토 이후 변경됨 |

차이가 없다는 관찰과 절대적 정확성을 구분합니다. 링크 존재·테스트 통과만으로 검토상 일치로 승격하지 않습니다. 일부 관계만 확인했다면 각각 구분해 기록합니다.

## 변경과 주기적 검토

PR에서 바뀐 내용과 연결된 규칙을 확인합니다. 문서·위키·코드 중 관련된 다른 쪽을 고치지 않아도 된다면 이유를 짧게 적습니다. 미구현인 동작을 문서에서 삭제해 정합성이 좋아진 것처럼 만들지 않습니다.

관련 파일이 변경되면 사람이든 에이전트든 마지막 확인 버전과 차이를 보고 재검토 필요로 표시합니다. 현재는 이 표시를 자동 갱신하지 않습니다. 정기 검토는 주간 CI 결과를 확인할 때 범위를 정해 수행하며, 실행자·발견 사항·미확인 범위를 기록합니다. 정기 LLM 실행과 자동 PR 생성은 설정하지 않았습니다.

기계 검사에는 파일·링크 존재, 스키마 예시, 테스트 등을 맡기고(문서에 적은 경로와 규칙 ID는 tests/test_docs_consistency.py가 확인) 의미 검토에는 조건·예외·테스트의 실효성을 맡깁니다. 에이전트는 근거 위치와 수정안을 제시하며, 기준 변경은 필요한 논의를 거칩니다.

| 연결 | 현재 상태 | 근거 |
|---|---|---|
| docs ↔ 위키 | 문서 참조 연결, 의미 검토 기록은 PR에 남김 | [금액 처리 안내](wiki/index.md#amount) |
| docs ↔ 코드 | 단위 변환 구현, 공시 추출은 미구현 | src/dartness/amounts.py 및 tests/test_amounts.py |
| 위키 ↔ 코드 | 입력·출력 범위와 구현 위치 연결 | [단위 처리 설명](amounts.md)과 금액 처리 위키 |

예상 확인 사례: 숫자·통화는 있지만 적용 단위가 없고 상위 문맥에서도 확인할 수 없는 입력. 기대 동작은 확인 필요이며 조건 충족으로 확정하지 않는 것입니다. 단위 변환의 정상·누락·지원하지 않는 단위·형식 오류 사례는 tests/test_amounts.py에 작성했습니다. 실제 공시 fixture와 추출 검증은 아직 없습니다.

## 현금 조회 규칙

규칙 원문은 [현금 조회 범위](requirements.md#cash-scope)에 있습니다. 예시와 실행 검사는 [현금 계약 예시](cash-query-contract.md#examples)에 있습니다. 계약·선정 구간 추출 검사는 선정된 기준일과 값이 어긋나는 대체를 거절합니다. 공통 계약의 날짜 후보 선택·표시는 검사하지만 원문 수집·공시 버전·추출을 연결한 엔진은 아직 없으므로 전체 정책을 검증했다고 해석하지 않습니다.

<a id="cash-001"></a>
규칙 **CASH-001**: 별도·개별 금액을 확인하지 못해도 연결 금액으로 대신 채우지 않습니다.

<a id="cash-002"></a>
규칙 **CASH-002**: 금액을 확인하지 못하면 0원으로 대신 채우지 않습니다. 확인 불가 결과에는 금액이 없습니다.

<a id="cash-003"></a>
규칙 **CASH-003**: 실제 자료의 기준일을 다른 시점의 금액으로 표시하지 않습니다. 허용 범위의 이전 자료를 사용하면 요청 기준일·실제 자료 기준일·대체 여부를 함께 표시합니다.

현재 검사는 선정된 추출 대상 기준일과 결과 기준일의 일치를 확인합니다. 원래 요청일·경과 한도·이전 자료 표시는 [공통 계약 v1](common-query-contract.md)과 tests/test_query_contract.py에서 검사합니다. 기존 현금 검사만으로 이 정책이나 원문 후보 선정까지 증명하지는 않습니다.

## 규칙과 검사의 연결

규칙 ID를 붙인 규칙에는 문서 예시나 테스트가 최소 하나 있어야 합니다. 아직 검사할 구현이 없으면 정의 끝에 (미구현)을 붙입니다. tests/test_docs_consistency.py가 이 연결을 확인합니다. 연결된 검사가 있다는 사실이 규칙을 빠짐없이 검증했다는 뜻은 아닙니다. 검사가 규칙의 핵심 실패를 실제로 재현하는지는 PR에서 검토합니다.

## 이슈 #15: 현금 범위와 개발 원칙 반영

2026-11-20 사용자가 현금 조회 범위와 다섯 개발 원칙을 승인했습니다. requirements.md의 현금 범위를 원본으로 두고 관리 화면 카드를 결정 완료로 변경했습니다. 별도·개별 기본, 연결 선택, 0원·연결 자동 대체 금지와 확인 불가 이유를 대조했습니다. 기존 헬릭스미스 연결 정답은 변경하지 않았습니다.

engineering-principles.md는 기존 검사·위임·탐색 구조에 원칙을 연결하고 cash-query-contract.md는 실행 스키마가 아닌 초안으로 표시했습니다. 위키·작업 상태·이슈/PR 양식과 관리 화면의 기준 링크를 갱신했습니다. 문서·코드의 모든 의미를 자동 평가하는 검사는 새로 만들지 않았습니다.

실행 평가: Python 43개·UI 6개 테스트, Ruff·mypy·UI 린트·타입·빌드·MkDocs strict가 통과했습니다. 이번 작업에서 실제 DART·유료 모델 평가는 실행하지 않았고 비용·사용자 리뷰 시간·개선 효과는 미측정입니다. 기존 테스트 결과는 현금 추출기의 정확도 근거가 아닙니다. UI 문구는 코드와 요구사항을 대조했으며 실제 브라우저·Vercel 배포는 미확인입니다. 최종 커밋의 CI와 병합 근거는 해당 PR에서 확인합니다.

## 이슈 #17: 현금 계약 v1 실행 평가

- 기준: requirements.md의 현금 범위와 cash-query-contract.md의 Python 계약 v1. src/dartness/cash_contract.py와 tests/test_cash_contract.py를 연결했습니다.

- 수정: 첫 타입 검사에서 의도적으로 잘못된 타입을 넣는 음성 테스트도 정적 오류로 잡혔습니다. 해당 테스트의 의도를 명시한 cast로 런타임 검증 경계를 검사하도록 수정했습니다. 검사 제외·ignore·기존 정답 변경은 없었습니다.
- 한계: 증거 필드의 존재·형식·범위·시점·정확한 단위 변환을 검사합니다. 원문에서 후보를 추출하거나 근거의 진실성을 자동 검증하지 않습니다. 비용·총 작업 시간·하네스 개선 효과는 미측정이며 추출 정확도 점수를 보고하지 않습니다.
- 사용자 관리: 사용자가 운영 화면 접속을 확인했고 상세 UI 검토를 보류했습니다. 이슈 #13은 그 합의로 종료했으며 기존 UI CI는 유지합니다.

후속 작업은 계약을 받을 원문 후보 추출 범위를 정하고 다른 법인·서식의 실제 사례를 확보하는 것입니다. 기준일 기본값·정정 선택·필터 포함 정책은 미결로 유지합니다. 최종 커밋과 CI·병합 근거는 관련 PR에 기록합니다.

## GitHub 상태 조회와 상태 요약 정리

이슈 #69는 저장본에 열린 것으로 남은 이슈 #67을 GitHub에서 닫힌 상태로 읽어야 한다는 실패에서 시작했습니다. 기대 동작·실패/취소 기준을 먼저 docs/management-screen.md에 적고 신규 로더 테스트가 모듈 부재로 실패한 뒤 구현했습니다. 기존 공개 조회 모듈을 브라우저/빌드에서 함께 사용하며 새 서버·토큰·권한·의존성을 추가하지 않았습니다.

세 요청의 완전한 성공·형식 검증 후에만 최신 자료로 바꾸고 부분 실패·403/429·네트워크·잘못된 응답은 대체 자료로 구분합니다. 재조회 실패는 직전 자료와 원래 시각을 유지하며, 초기 실패는 저장본을 사용하고 둘 다 실패하면 정상 빈 목록을 만들지 않습니다. 취소된 요청은 이전 자료를 새 결과로 반환하지 않도록 검사합니다.

현재 지원 여부는 시스템 상태와 연결된 기준 문서에서 확인하도록 개발 원칙의 오래된 추출/평가 미구현 문구를 링크로 바꿨습니다. 관리 화면의 배포 미확인 설명은 기존 PR·배포 근거로 정정했습니다. 이는 요구사항을 코드에 맞춰 바꾼 것이 아니라 합의된 구현 상태의 중복 기록을 줄인 것입니다. docs·브리핑은 배포 커밋 기준이며 GitHub 상태의 조회 시각과 구분합니다. 기존 DART 기대값·CI 검사·위임 정책은 유지합니다.

로컬 Chromium의 통제 응답 흐름은 저장본→최신 조회→실패 시 직전 자료 유지와 페이지 오류 0건을 확인했습니다. 외부 직접 TLS의 환경 제약은 관리 화면 문서에 남겼고, TLS 검증을 유지한 환경 프록시/CA HTTP 클라이언트로 실제 GitHub 세 응답 200을 확인했습니다. 앱의 TLS 설정이나 검증 조건은 바꾸지 않았습니다.

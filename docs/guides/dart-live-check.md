# DART 실제 수집 검사

이슈 #9의 수동 연동 검사입니다. 사용자에게 등록받은 DART_API_KEY를 Actions 환경변수로만 사용합니다. 일반 PR CI에서는 키 없이 고정 응답 테스트만 실행합니다.

## 검사 범위

1. corpCode.xml에서 종목코드 084990인 헬릭스미스의 법인코드를 확인합니다.
2. list.json에서 2026.03.20에 접수된 사업보고서 (2025.12)를 찾습니다. 다른 날짜·보고서를 자동 대체하지 않습니다.
3. 후보가 정확히 하나인 경우 document.xml에서 원문 ZIP을 내려받고 비어 있지 않은 XML 파일 존재를 확인합니다.

정상 실행은 요청 3회입니다. 최대 다운로드 32MiB, ZIP 내부 총크기 128MiB, 파일 수 100개, HTTP 요청별 제한시간 30초, Actions 작업 제한시간 5분을 둡니다. 자동 재시도와 페이지 추가 조회는 없으며 예상 밖의 결과는 실패로 표시합니다. 이것은 첫 수집 경로 검사이지 전체 법인용 클라이언트나 캐시 구현이 아닙니다.

원문 ZIP과 각 XML의 SHA-256, 실제 DART 접수번호·법인코드·공시일·출처 링크를 기록합니다. 보고서 이름에서 읽은 2025.12와 원문에서 검증한 재무 기준일을 혼동하지 않습니다. 재무 기준일·연결/별도·금액·정정 관계는 아직 검증하지 않습니다.

## 실행

저장소 Settings → Secrets and variables → Actions에 DART_API_KEY를 등록합니다. Actions의 Check code → Run workflow에서 대상 브랜치와 dart_smoke=true를 선택합니다. 기본값은 false입니다. main에 이미 있는 workflow_dispatch를 작업 브랜치에서도 실행할 수 있도록 같은 워크플로에 수동 작업을 추가했습니다.

명령으로 실행할 때는 다음과 같습니다. 시크릿 값은 명령에 넣지 않습니다.

```bash
gh workflow run code.yml --ref feat/9-dart-smoke -f dart_smoke=true
```

병합 후에는 --ref main으로 실행합니다. 사용자 요청이 있을 때만 수동 실행하며 PR·예약 실행에서 실제 DART를 호출하지 않습니다. 기존 code-quality 필수 검사는 유지하고 dart-smoke는 외부 서비스 장애를 이유로 일반 PR을 막지 않도록 별도로 둡니다.

## 실패와 키 보호

키 누락·형식 오류, 인증 오류, IP 제한, 자료 없음, 요청 제한, 점검, 네트워크·HTTP 실패를 구분합니다. 원래 예외 메시지·인증키 포함 URL·서버 메시지는 출력하지 않습니다. HTTP 리다이렉트는 차단합니다. 응답·산출물에 키가 포함됐는지 검사하고 발견되면 저장하지 않습니다.

API 인증 실패는 추출 결과가 없다는 뜻이 아닙니다. 자료 없음과 원문 누락도 성공으로 기록하지 않습니다. 구체적인 실패 원인을 확인한 후 필요한 수정만 수행합니다.

## 결과와 보관

성공하면 dart-smoke-실행번호 아티팩트에 manifest.json과 document.zip을 3일 보관합니다. 공개 저장소의 아티팩트 접근 범위를 고려해 이 검사는 공개 공시만 대상으로 하며 내부 목록은 넣지 않습니다. 원문·키·생성 결과를 Git에 자동 커밋하지 않습니다. work/는 Git에서 제외합니다.

manifest의 collected는 수집 성공입니다. LLM 해석, 재무금액 정답 검증, KIND와 DART 원문의 동등성까지 확인했다는 뜻은 아닙니다. 실제 API 실행 결과는 PR·이슈 기록으로 남기며 성공 전에는 유효한 키라고 단정하지 않습니다.

## 오프라인 테스트

tests/test_dart_smoke.py에서 가짜 응답으로 회사·보고서 일치, 페이지 누락 방지, 오류 상태, XML/ZIP 실패, 비밀값을 노출하지 않는 오류 처리를 확인합니다. 이 테스트가 실제 DART 서비스의 정상 동작을 보증하지는 않습니다.

API 키의 값은 문서·테스트에 적지 않습니다. 계약·응답이 달라지면 공식 문서를 다시 확인하고 문서·코드·테스트를 함께 고칩니다. 저장한 규격을 최신이라고 영구 가정하지 않습니다.

개발 에이전트가 규격을 확인하는 과정과 조회 에이전트가 도구를 실행하는 과정을 구분합니다. 실제 조회 때마다 웹검색으로 엔드포인트·필드를 만들어내지 않습니다. API가 늘면 필요한 규격을 추가하고 공식 문서 링크를 찾는 비용이 커질 때 문서 검색·임베딩의 필요성을 평가합니다. 외부 DART MCP·스킬·래퍼는 도입하지 않고 공식 OpenDART API를 직접 호출합니다.

## 평가용 여러 법인 수집

2026-11-23 사용자가 다른 법인 평가(이슈 #31)의 원문을 GitHub Actions로 받기로 했습니다. 이 세션 환경에서는 DART 웹·KIND가 자동 요청을 거절하고, Actions 결과 파일(artifact)의 내려받기 주소도 네트워크 정책에 막혀 있습니다. 그래서 수집 결과를 별도 데이터 브랜치에 저장하는 방식을 택했습니다.

- **실행:** Actions의 **Collect DART filings**를 수동 실행합니다. 입력은 종목코드(최대 8개)와 사업연도입니다. 코드는 src/dartness/dart_collect.py, 테스트는 tests/test_dart_collect.py입니다.
- **수집 내용:** 법인마다 기업개황의 결산월, 해당 연도 사업보고서 원본(정정 전) 1건의 원문 ZIP, OpenDART 재무제표 API의 별도(OFS)·연결(CFS) 응답을 받습니다. 정정 보고서는 이름만 기록합니다. 요청 수는 1 + 법인 수 × 5회 이하이며, 요청마다 30초·32MiB 제한을 기존 수집과 같이 적용합니다.
- **결과:** `data/dart-filings-실행번호` 브랜치에 manifest.json과 원문을 커밋합니다. 이 브랜치는 main에 병합하지 않습니다. 평가에 쓸 재무상태표 구간만 골라 테스트 사례로 옮기고, 원문 해시로 출처를 남깁니다.
- **권한:** 이 작업에만 `contents: write`를 줍니다. 일반 PR 검사는 읽기 권한만 가집니다. 키는 저장소 비밀값으로만 쓰고, 결과에 키가 들어 있으면 저장하지 않고 실패합니다.

### 12월이 아닌 결산 법인

2026-11-23 이슈 #58에서 정했습니다. 결산월은 법인마다 OpenDART 기업개황 API(`company.json`)의 `acc_mt`로 확인합니다. 짐작하거나 고정하지 않습니다.

- **사업연도:** 입력한 사업연도는 결산일이 속한 해입니다. 예를 들어 3월 결산 법인의 2025 사업연도 보고서는 `사업보고서 (2025.03)`, 12월 결산 법인은 지금처럼 `사업보고서 (2025.12)`입니다.
- **공시 검색 기간:** 결산일 다음 날부터 1년 동안 낸 공시에서 찾습니다. 12월 결산은 다음 해 1월 1일~12월 31일로, 지금과 같습니다.
- **요청 수:** 법인마다 기업개황 1회가 늘어 1 + 법인 수 × 5회 이하입니다.
- **실패:** 결산월이 없거나 01~12가 아니면 그 법인은 `invalid_fiscal_month`로 남기고 다른 법인은 계속 받습니다.
- **API 대조값:** 12월이 아닌 결산 법인에서 재무제표 API가 사업연도를 같은 뜻으로 쓰는지는 확인하지 않았습니다. 그래서 API 응답의 접수번호가 받은 원문의 접수번호와 같은지를 manifest에 `matches_report`로 남깁니다. 같지 않으면 그 값으로 정답을 교차 확인하지 않습니다.

재무제표 API 값은 원문에서 확인한 정답을 **교차 확인**하는 데만 씁니다. API 값으로 정답을 만들지 않습니다. API는 XBRL 기반이라 원문 표와 기간·범위 표기가 다를 수 있습니다. 이 수집은 원문을 받을 뿐 현금을 추출하거나 정답을 정하지 않습니다.

이전 헬릭스미스 수집에서는 원문 ZIP을 Git에 저장하지 않았습니다. 이번에는 결과를 이 세션으로 가져올 다른 방법이 없어 데이터 브랜치에 저장합니다. 공개 공시 원문이며 main 이력에는 들어가지 않습니다.

## 외부 DART 도구 사용 결정

2026-11-20 사용자와 결정했습니다. 다른 사람이 만든 DART MCP·스킬·전용 API 래퍼는 실행 의존성으로 도입하지 않습니다. 공식 OpenDART API를 직접 호출하고 선택·오류 처리·검증 규칙을 Dartness의 코드와 테스트로 관리합니다.

Python·린트·타입 검사·테스트·문서 사이트 등 범용 도구까지 금지하는 결정은 아닙니다. 이전 추천안에 나온 외부 DART 저장소는 채택된 의존성이 아닙니다. 자체 구현도 공식 규격과 실제 공시 사례로 검증합니다.

## 지정 접수번호의 전체 원문 수집

정정 연결 이슈 #101에서 필요한 원본·정정 전체 제출서류를 확보하기 위한 수집 모드입니다. 기존 Collect DART filings 워크플로에 collection_mode=exact_receipts와 receipt_numbers를 명시하면 접수번호 1~2건의 document.xml API만 호출합니다. 기본 annual 모드의 종목코드·사업연도 기반 원본 평가 수집은 유지합니다. 지정 수집에서 종목코드 기본값·재무제표 API·원본 선택 규칙을 대신 실행하지 않습니다.

접수번호는 서로 다른 14자리 숫자여야 하며 수집 전에 개수/형식을 검증합니다. API 요청은 최대 2회, 기존 요청당 30초·32MiB와 ZIP 제한을 그대로 사용합니다. 원문 ZIP에 정확히 접수번호.xml 본문이 있어야 합니다. 첨부를 대신 쓰지 않으며 한 건이라도 실패하면 전체 지정 묶음은 완료 결과로 반환/저장하지 않습니다. 인증키는 기존 저장소 비밀값과 같은 전송 경로만 사용하고, 압축 출력 내부에도 키가 없는지 검사합니다.

결과는 기존처럼 main에 병합하지 않는 data/dart-filings-실행번호 브랜치의 manifest.json과 원문 ZIP입니다. manifest의 complete는 지정한 접수번호 묶음 수집만 뜻하며 전체 공시 이력·정정 관계·최신 유효성·금액 추출을 뜻하지 않습니다. 전체 ZIP과 본문/XML 멤버 해시를 구분해 기록합니다. 실행 코드: src/dartness/dart_receipts.py, 기존 진입점: src/dartness/dart_collect.py. 고정 응답 검사는 tests/test_dart_receipts.py이고 일반 PR CI에서 실제 API를 호출하지 않습니다. 새 시크릿·권한·의존성·상시 실행은 추가하지 않습니다.

# 테스트를 작성하고 확인하는 방법

상태: 첫 사례의 작은 차이 표시 기준은 사용자와 합의했습니다. 선정된 단순 재무상태표 구간의 현금 추출 테스트가 있으며 전체 문서·다른 유형의 추출 평가는 아직 없습니다. 원문 대조는 에이전트가 수행했습니다.

테스트는 구현이 지금 하는 일을 복사하는 대신, docs에 정한 동작과 공시 원문을 기준으로 작성합니다. 코드는 에이전트가 작성하되 기대 결과가 어디서 나왔는지 확인할 수 있어야 합니다.

## 작성 순서

1. **기준 확인:** 관련 docs와 규칙 ID를 읽습니다. 모호한 기준은 질문으로 남기고 구현 출력에 맞춰 결정하지 않습니다.
2. **사례 준비:** 원문에서 정상 사례와 오류·판단 보류 사례를 고릅니다. 원문을 변경한 사례는 실제 공시와 구분합니다.
3. **정답 작성:** 숫자·기간·단위·연결/별도·근거 위치를 원문에서 확인합니다. 구현 함수를 실행해 정답을 만들지 않습니다.
4. **테스트 작성:** 기대 결과와 금지할 결과를 함께 검사합니다. 단위가 없을 때 확인 필요인지, 금액을 0으로 반환하지 않는지도 확인합니다.
5. **구현·수정:** 버그 수정은 먼저 재현 테스트가 실패하는지 확인합니다. 새 기능은 가능하면 기대 동작 테스트부터 작성하되 문서만 수정할 때 형식적인 테스트를 추가하지 않습니다.
6. **다른 사례로 확인:** 개발에 맞춰 수정한 회사와 다른 회사·서식·기간의 공시로 평가합니다.
7. **PR 검토:** 어떤 원문으로 무엇을 확인했고 무엇은 아직 모르는지 기록합니다. 기대 결과·검사 제외를 바꿨다면 이유를 설명합니다.

## 정답 사례에 남길 내용

| 항목 | 기록할 내용 |
|---|---|
| 출처 | 제공기관·URL·문서 종류·법인·조회일·원문 해시 |
| 시간 | 공시일·재무 기준일·비교 기간·정정 여부의 확인 상태 |
| 범위 | 연결/별도·통화·표 단위와 그 근거 |
| 값 | 원문 숫자, 적용 단위, 정확히 변환한 값 |
| 위치 | 절·표·행·열 및 필요한 주변 문장 |
| 대조 | 어떤 세부항목을 합산했는지, 총액과 차이 |
| 검토 상태 | 작성자·검토일·확인 방법·사용자 확인 여부 |

원본 문서 해시와 부분 발췌 해시를 혼동하지 않습니다. 주석 표만으로 단위·기간이 보이지 않으면 해당 표를 충분한 입력으로 취급하지 않습니다. 내부 목록·키·불필요한 전체 원문은 공개 저장소에 넣지 않습니다.

## 개발용과 별도 검증용

- **개발용:** 파서·프롬프트를 만들며 반복해서 확인하는 사례입니다.
- **별도 검증용:** 개발에 사용하지 않은 다른 법인·서식 사례입니다. 평가 전 기대 결과를 고정하고 버전을 남깁니다.
- 검증용 사례를 보고 구현·프롬프트를 수정했다면 그 사례를 계속 미사용 검증용이라고 부르지 않습니다. 새로운 사례로 다시 평가합니다.
- 공개 저장소에서는 파일을 숨겨 모델이 절대 볼 수 없다고 보장할 수 없습니다. 목적은 평가 사례로 반복 튜닝한 성능과 새 사례의 성능을 구분하는 것입니다.

첫 [헬릭스미스 사례](../cases/helixmith-cash.md)는 이미 읽고 분석했으므로 개발용입니다. 별도 검증용 사례는 아직 선정하지 않았습니다.

## 테스트의 역할

| 검사 | 실행 방식 | 확인하는 것 |
|---|---|---|
| 단위·계산 테스트 | 일반 CI, 고정 입력 | 정확한 계산과 실패 상태 |
| 문서 예시 검사 | 일반 CI | 문서에 적힌 예시와 실제 코드 결과 |
| 공시 파싱·계약 테스트 | 구현 후 일반 CI, 저장된 원문 조각 | 기간·단위·셀 위치 보존, 입력·출력 규칙 |
| API 연동 검사 | 별도 실행 | 다운로드·오류·정정·호출 제한 처리 |
| 실제 LLM 평가 | 별도 실행 | 원문 의미·기간·단위·근거의 정확성 |

API·LLM 응답을 고정한 테스트는 후속 코드가 그 응답을 처리하는지만 확인합니다. 실제 모델의 해석 정확성을 검증했다고 설명하지 않습니다. 실제 LLM 평가는 모델·프롬프트·입력·도구·실행 시점과 반복 실행 결과를 기록하고 시간·비용 한도를 둡니다.

## 문서 예시 테스트

문서에 적은 동작을 테스트가 실제로 실행해 확인하는 방식입니다. 2026-11-20 사용자와 정한 범위는 규칙 ID가 붙은 규칙입니다. 그 밖의 문서에도 예시를 쓸 수 있지만 요구하지는 않습니다.

### 언제 쓰나요?

[정합성 검토](../consistency.md)에서 규칙 ID를 붙인 규칙에는 문서 예시나 테스트가 최소 하나 있어야 합니다. 테스트가 규칙을 검사한다면 테스트 코드에 규칙 ID를 적어 연결합니다. 아직 검사할 구현이 없으면 규칙 정의 끝에 (미구현)을 붙입니다. 미구현 규칙에 통과하는 형식적인 예시를 만들지 않습니다.

### 어떻게 쓰나요?

예시 블록 바로 위에 `<!-- dartness-example: 이름 -->` 표식을 둡니다. 표식은 사이트에 보이지 않습니다. 블록은 JSON 목록이고 각 항목은 아래 필드를 씁니다.

| 필드 | 필수 | 내용 |
|---|---|---|
| id | 예 | 저장소 전체에서 겹치지 않는 예시 이름. 실패 로그에 표시됩니다 |
| rule | 아니요 | 이 예시가 확인하는 규칙 ID |
| source | 예 | synthetic(합성), real-dev(실제 공시·개발용), modified(실제 값을 변형하거나 다른 요청에 넣음) |
| input | 예 | 테스트가 함수에 넘길 값 |
| expect | 예 | 기대 결과. 결과 필드와 값을 적습니다. null은 그 필드가 없어야 한다는 뜻입니다. 거절이면 error에 예외 이름, message에 오류 문구 일부를 적습니다 |

예시는 정상 결과만이 아니라 금지할 결과도 보여줘야 합니다. 예를 들어 "단위 없음 → 확인 필요, 금액 필드 없음"처럼 씁니다. 거절 예시는 message로 거절 이유를 고정합니다. 다른 이유로 거절돼도 통과하는 일을 막기 위해서입니다.

### 테스트는 어떻게 만드나요?

tests/doc_examples.py의 load_examples("이름")로 블록을 읽고 check_example로 비교합니다. 모듈마다 input을 실제 함수 호출로 바꾸는 부분만 작성합니다. check_example은 expect에 적힌 모든 필드를 비교합니다. 상태만 비교하지 않도록, 그 규칙에서 중요한 필드(금액, 기준일, 범위, 이유)를 expect에 적습니다.

### 바꿀 때의 규칙

- 기대값은 사람이 명세나 원문에서 정합니다. 구현을 실행한 출력을 복사해 채우지 않습니다.
- real-dev 값은 원문 대조 기록이 있는 사례에서만 가져옵니다. 출처 사례를 문서에 적습니다.
- 이미 있는 예시의 expect를 바꾸는 것은 기존 정답 변경입니다. [위임 정책](delegation.md)에 따라 사용자 확인을 받습니다. 표기 형식만 옮길 때는 PR에 값이 같다는 것을 보여줍니다.

### CI가 확인하는 것과 못 하는 것

tests/test_docs_consistency.py와 각 예시 테스트가 다음을 실패로 처리합니다.

- 예시의 기대 결과와 실제 코드 결과가 다를 때
- 어떤 테스트도 읽지 않는 예시 블록이 있을 때
- id가 겹치거나 source·input·expect 형식이 틀릴 때
- 예시가 정의되지 않은 규칙 ID를 쓸 때
- (미구현)이 아닌 규칙에 예시도 테스트도 없을 때

적힌 예시에 대해서만 문서와 코드가 맞는지 확인합니다. 예시가 규칙의 중요한 실패를 빠짐없이 다루는지, 문서의 다른 문장이 코드와 맞는지는 확인하지 않습니다. 그 판단은 PR의 정합성 검토에서 합니다.

## 변이 테스트

에이전트가 코드와 테스트를 함께 쓰면 테스트가 구현을 따라 써져 버그를 못 잡을 수 있습니다. 변이 테스트는 코드를 일부러 조금씩 바꾼 변이(예: `>`를 `>=`로, `or`를 `and`로)를 만들고, 테스트가 각 변이를 실패로 잡는지 셉니다. 테스트를 통과한 변이는 "살아남은 변이"이며, 테스트가 그 변화를 구분하지 못한다는 뜻입니다.

2026-11-23 사용자가 `mutmut` 시험 도입을 승인했습니다(이슈 #41). 지금은 src/dartness/cash_table.py만 대상으로 하며 CI에서 실행하지 않습니다.

### 실행 방법

```bash
python -m pip install -r requirements-mutation.txt
```

```bash
python -m mutmut run
```

```bash
python -m mutmut results
```

설정은 pyproject.toml의 `[tool.mutmut]`에 있습니다. 결과는 `mutants/`에 생기며 저장소에 커밋하지 않습니다. 살아남은 변이는 `python -m mutmut show 이름`으로 바뀐 코드를 봅니다. 한 번 실행에 약 10초 걸립니다.

### 첫 결과 (cash_table.py, 변이 339개)

| 시점 | 살아남은 변이 | 잡은 비율 |
|---|---|---|
| 테스트 보강 전 | 82개 | 76% |
| 테스트 보강 후 | 26개 | 92% |

보강 전에 살아남은 변이는 대부분 한 원인에서 나왔습니다. 추출 실패는 모두 `extraction_failed`로 돌아오는데, 테스트가 이유(`detail`)를 보지 않았습니다. 그래서 앞쪽 검사가 망가져도 뒤쪽 검사가 같은 입력을 걸러 테스트가 통과했습니다. 변형 입력마다 어떤 검사가 걸렸는지 `detail`로 확인하도록 바꿨습니다.

그 밖에 보강한 빈틈은 다음과 같습니다.

- 표 구조가 깨진 HTML: 행 밖의 셀, 표 밖의 행, `</TD>`·`</TR>` 중복, 짝이 맞지 않는 닫는 태그. `</TD>`나 `</TR>`이 중복되면 일부 변이에서 확인 필요 대신 예기치 않은 오류로 멈췄습니다.
- `<style>`, `rowspan`, 명시적인 `colspan="1"`.
- 경계값: 구간 크기 256KiB 정확히(허용)와 1바이트 초과(거절), 요청 기간 열 하나만 있는 표.
- 셀 안의 태그와 문자 참조로 나뉜 글자, 개별재무제표(individual) 요청, 성공 결과의 근거 위치·문맥.

남은 26개는 결과가 달라지지 않는 동등 변이로 판단했습니다. 24개는 오류 문구 앞뒤에 글자를 붙인 변이로, 테스트가 문구의 핵심 부분만 확인하기 때문에 살아남습니다. 2개는 항상 덮어쓰이는 초깃값(`cell_tag`)입니다.

### 테스트를 쓰다 확인한 현재 동작

금액 표의 왼쪽 위 칸이 비어 있지 않으면(예: "과목") 머리글 구조 오류로 확인 필요를 돌려줍니다. 헬릭스미스 원문은 이 칸이 비어 있지만, 다른 법인 공시에는 "과목"이 흔할 수 있습니다. 이 동작은 테스트로 고정만 했고 바꾸지 않았습니다. 다른 법인 평가(이슈 #31)에서 확인합니다.

### 한계

- 변이 점수는 테스트가 코드 변화를 구분하는지 보여줄 뿐입니다. 추출이 실제 공시에서 맞는지는 증명하지 않습니다. 그건 원문 기반 평가의 몫입니다.
- 동등 변이 판단은 사람이나 에이전트의 검토이며, 도구가 증명한 것이 아닙니다.
- 다른 모듈로 넓히거나 CI에서 실행할지는 아직 정하지 않았습니다.

## 테스트 리뷰 기준

- 성공 상태뿐 아니라 금액·기간·단위·근거 등 해당 작업의 중요한 필드를 비교합니다.
- 합계 계산은 입력에 적힌 총액을 그대로 반환하도록 모킹해 통과시키지 않습니다.
- 원문에 없는 내용을 정답에 추가하지 않습니다. 빈칸·대시를 자동으로 0으로 간주하지 않습니다.
- 테스트가 실패하면 구현·정답·명세 중 어디가 잘못됐는지 먼저 확인합니다. 통과시키기 위해 정답을 바꾸지 않습니다.
- 같은 에이전트가 작성하고 검토했다고 독립 검증이라고 부르지 않습니다. 원문 대조·독립 계산·사용자 확인의 범위를 따로 기록합니다.
- 테스트 개수나 커버리지 목표보다 놓치면 안 되는 사례를 우선합니다. 아직 검사할 구현이 없는 초안을 통과 테스트로 포장하지 않습니다.

[개발 원칙](../design/engineering-principles.md)에 따라 DART 결과와 개발 과정 평가는 구분합니다. 실행 조건·실패·미측정 항목은 [평가 기록 양식](../record-forms/evaluation.md)으로 남길 수 있습니다.

## 정확성 평가

금액만 맞아도 기간·통화·연결/별도가 틀리면 정답이 아닙니다. 검토한 필드와 사례 수를 함께 보고합니다. 잘못된 확정, 누락, 확인 필요 비율을 구분하며 모두 보류해 오류가 적어 보이는 것을 성공으로 보지 않습니다. 한 사례로 전체 공시 성공률을 주장하지 않습니다.

## 현재와 다음 단계

금액 단위 변환과 문서 예시는 tests/test_amounts.py가 검사합니다. 이슈 #7의 주석 자료는 합계 검증용 초안입니다. 별도·연결 재무상태표 구간은 이슈 #19의 제한된 추출 테스트에 연결했습니다. 합의한 표시 기준을 바탕으로 필요한 입력·출력 계약과 실패 사례를 함께 정하고 다음 구현 이슈로 이어갑니다. 자동 차이 판정과 전체 보고서의 절 선정·범용 추출은 아직 구현하지 않았습니다.

## 현금 계약 v1 검사

이슈 #17의 tests/test_cash_contract.py는 실제 공시에서 먼저 확인한 별도·연결 값 두 개와 합성한 실패 입력을 검사합니다. 추출 테스트는 아닙니다. [계약과 검증 범위](../specs/cash-query-contract.md)에서 타입·시점·범위·단위·근거 검사의 한계를 확인합니다.

## 예외 처리·검사 우회 검사

[예외 처리·우회 기준](quality-guards.md)에 따라 실제 Ruff 반례와 구체 예외 처리의 허용 사례를 검사합니다. PR base/head의 새 무시·테스트 비활성 구문은 기존 테스트와 별도로 비교합니다. 예시 문자열 속 우회 이름은 실제 지시문으로 간주하지 않고, 기존 불변성·잘못된 입력 테스트의 명시적 type-ignore는 유지합니다. 모든 정답 변경이나 assert 약화를 탐지하는 검사는 아닙니다.
